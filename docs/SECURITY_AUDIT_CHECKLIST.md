# Security Audit Checklist for Cloud Deployment

**Last Updated**: Phase 5  
**Purpose**: Verify security posture before and after cloud deployment  

---

## Pre-Deployment Audit

### 1. Environment Variables & Secrets Management

#### 1.1 Local Development
- [ ] `.env` file exists in `.gitignore`
- [ ] `.env` file NOT committed to GitHub
- [ ] `.env.example` exists and is committed (template without secrets)
- [ ] No secrets hardcoded in application code
- [ ] No secrets in Docker files or docker-compose.yml

**Verify**:
```bash
# Check .gitignore contains .env
grep "^.env$" .gitignore

# Check .env is not in git tracking
git ls-files | grep -E "\.env$"
# Should return nothing
```

#### 1.2 Secrets in Code
- [ ] No API keys in source files
- [ ] No database passwords in source files
- [ ] No JWT secrets in source files
- [ ] All configuration loaded from environment

**Verify**:
```bash
# Search for common secret patterns
grep -r "password" backend/app --include="*.py" | grep -v ".env"
grep -r "api_key" backend/app --include="*.py" | grep -v ".env"
grep -r "secret" backend/app --include="*.py" | grep -v ".env"
# Should find only configuration loading code
```

#### 1.3 JWT Secret Quality
- [ ] Local JWT_SECRET is at least 32 characters
- [ ] Cloud JWT_SECRET is DIFFERENT from local
- [ ] JWT_SECRET was generated with `secrets.token_hex()` or similar
- [ ] JWT_SECRET is NOT a default/weak value

**Verify**:
```bash
# Check local JWT_SECRET length
python -c "import os; print(len(os.environ['JWT_SECRET']))"
# Should be >= 32
```

### 2. Database Security

#### 2.1 Connection Security
- [ ] DATABASE_URL never hardcoded in code
- [ ] DATABASE_URL uses `sslmode=require` for cloud deployments
- [ ] Database password is NOT the default
- [ ] Database password is sufficiently random/strong

**Connection Strings**:
- ✅ Local: `postgresql://rag_user:rag_password@localhost:5432/secure_rag` (local dev OK)
- ✅ Cloud: `postgresql://user:strong_password@host.neon.tech/dbname?sslmode=require` (SSL required)
- ❌ Cloud: `postgresql://user:password@host/dbname` (missing sslmode=require)

#### 2.2 Database Access Control
- [ ] Only database owner can modify schema
- [ ] Application uses read/write role (not superuser)
- [ ] Database backups enabled (Neon has automatic backups)
- [ ] No public internet access to database

**Verify in Neon**:
1. Dashboard → Project → Branches
2. Look for "Backups" section
3. Verify automatic backups are enabled

#### 2.3 Migrations
- [ ] Alembic migrations tracked in git
- [ ] Migrations run automatically at startup
- [ ] No raw SQL in application code
- [ ] Schema changes follow Alembic workflow

**Current Status**:
- ✅ Backend auto-runs `init_db()` at startup
- ✅ Alembic configuration in place
- ⚠️ For production, consider:
  ```bash
  # Manual migration if needed
  cd backend && alembic upgrade head
  ```

### 3. Vector Database (Qdrant) Security

#### 3.1 API Key Management
- [ ] QDRANT_API_KEY is set for cloud deployments
- [ ] QDRANT_API_KEY is NOT hardcoded
- [ ] QDRANT_API_KEY is generated by Qdrant, not user-chosen
- [ ] QDRANT_API_KEY is different from JWT_SECRET

**Verify**:
```bash
# Check that API key is loaded from environment
python -c "from app.core.config import settings; print('API key set' if settings.qdrant_api_key else 'No API key')"
```

#### 3.2 Collection Configuration
- [ ] Collection name is consistent (`knowledge_chunks`)
- [ ] Vector size matches embedding model (384 for all-MiniLM-L6-v2)
- [ ] Distance metric is appropriate (Cosine recommended)
- [ ] No sensitive data in collection metadata

#### 3.3 Qdrant Cloud Access
- [ ] Qdrant API key has least privilege
- [ ] Qdrant endpoint URL is HTTPS
- [ ] No IP restrictions needed (Qdrant Cloud uses API key auth)

**Verify URL Format**:
- ✅ Cloud: `https://xxxxx-us-east1-0.qdrant.io:6333` (HTTPS)
- ✅ Local: `http://localhost:6333` (HTTP OK for local)
- ❌ Cloud: `http://xxxxx-...` (HTTP, insecure)

### 4. LLM Service (Azure OpenAI) Security

#### 4.1 API Key Management
- [ ] AZURE_OPENAI_API_KEY is NOT hardcoded
- [ ] AZURE_OPENAI_API_KEY never logged
- [ ] AZURE_OPENAI_API_KEY rotated periodically (recommended)
- [ ] AZURE_OPENAI_API_KEY limited to specific operations

**Code Review**:
```bash
# Check if API key might be logged
grep -r "AZURE_OPENAI_API_KEY" backend/app --include="*.py"
# Should only find config.py

# Check Azure client initialization
grep -r "api_key=" backend/app --include="*.py"
# Should use settings.azure_openai_api_key (from env)
```

#### 4.2 Endpoint Security
- [ ] AZURE_OPENAI_ENDPOINT is HTTPS
- [ ] AZURE_OPENAI_ENDPOINT is from correct Azure subscription
- [ ] API version is current (2024-12-01-preview or later)
- [ ] No test endpoints used in production

**Verify Format**:
- ✅ `https://my-resource.openai.azure.com/` (HTTPS, correct)
- ❌ `http://my-resource.openai.azure.com/` (HTTP, insecure)
- ❌ `https://api.openai.com/` (Public OpenAI, not Azure)

#### 4.3 Rate Limiting
- [ ] Azure deployment has quota configured
- [ ] Rate limit protection enabled
- [ ] Unexpected API calls monitored

### 5. CORS Configuration

#### 5.1 Origins List
- [ ] CORS_ORIGINS environment variable set
- [ ] CORS_ORIGINS NOT using wildcard `*`
- [ ] CORS_ORIGINS includes only known domains
- [ ] Local dev origins different from production

**Correct Formats**:
- ✅ Local: `http://localhost:3000,http://localhost:5173`
- ✅ Cloud: `https://yourdomain.com,https://frontend.onrender.com`
- ❌ `*` (wildcard - security risk)
- ❌ `http://*` (still wildcard)

**Verify in Code**:
```bash
# Check CORS configuration in main.py
grep -A 5 "CORSMiddleware" backend/app/main.py
# Should use settings.cors_origins (environment-driven)
```

#### 5.2 Methods & Headers
- [ ] CORS methods restricted if possible (not `["*"]` for production)
- [ ] CORS headers validated before use
- [ ] Credentials flag set correctly (true if sending auth)

**Current Code** (review):
```python
app.add_middleware(
    CORSMiddleware,
    allow_origins=cors_origins,  # Environment-driven
    allow_credentials=True,
    allow_methods=["*"],  # OK for now
    allow_headers=["*"],  # OK for now
)
```

### 6. Authentication & Authorization

#### 6.1 JWT Implementation
- [ ] JWT tokens include exp (expiration)
- [ ] JWT tokens never logged
- [ ] JWT tokens validated on every request
- [ ] JWT expiration time is reasonable (1 hour in config)

**Verify**:
```bash
# Check JWT implementation
grep -r "decode" backend/app/dependencies --include="*.py"
grep -r "exp" backend/app/models --include="*.py"
```

#### 6.2 MCP Token Authentication
- [ ] MCP token validated before processing
- [ ] MCP token expiration enforced (365 days)
- [ ] Backend generates short-lived JWT from MCP token
- [ ] No credentials sent in tool parameters

**Flow Verification**:
- ✅ MCP Client → Bearer token in headers → MCP Server validates
- ✅ MCP Server → POST /api/internal/mcp/validate → Backend checks
- ✅ Backend → Creates JWT → Returns to MCP Server
- ✅ MCP Server → Uses JWT for /api/chat calls

#### 6.3 Password Storage
- [ ] User passwords hashed with bcrypt/scrypt (not plaintext)
- [ ] Password hash table has `password_hash` column (not `password`)
- [ ] Password comparison uses constant-time algorithm

**Verify**:
```bash
# Check password storage implementation
grep -r "password_hash" backend/app --include="*.py"
# Should find hashing in password_service.py
```

### 8. Transport Layer Security

#### 8.1 HTTPS Enforcement
- [ ] All cloud services use HTTPS
- [ ] Self-signed certificates not used in production
- [ ] Certificate validation enabled

**URLs**:
- ✅ Render: `https://my-backend.onrender.com`
- ✅ Neon: `postgresql://...?sslmode=require`
- ✅ Qdrant Cloud: `https://....qdrant.io`
- ❌ Localhost: `http://localhost:8000` (OK for dev only)

#### 8.2 HTTP Headers
- [ ] HSTS headers enabled (long-term)
- [ ] X-Content-Type-Options: nosniff
- [ ] X-Frame-Options: DENY (if applicable)
- [ ] Security headers set by FastAPI middleware

**Note**: FastAPI doesn't set these by default. For production, consider:
```python
from fastapi.middleware.trustedhost import TrustedHostMiddleware

app.add_middleware(
    TrustedHostMiddleware,
    allowed_hosts=["yourdomain.com", "*.onrender.com"]
)
```

## Post-Deployment Verification

### 13. Service Health

- [ ] Backend health check passes: `GET /health` → `{"status": "healthy"}`
- [ ] MCP health check passes: `GET /health` → (valid response)
- [ ] Database logs show "Database initialized"
- [ ] Qdrant logs show "Qdrant initialized"
- [ ] No startup errors in Render logs

### 14. Security Headers Test

**From Browser Console**:
```javascript
// Check response headers
fetch('https://your-backend.onrender.com/health')
  .then(r => {
    console.log('Strict-Transport-Security:', r.headers.get('strict-transport-security'));
    console.log('X-Content-Type-Options:', r.headers.get('x-content-type-options'));
    return r.json();
  })
  .then(console.log);
```

### 15. CORS Verification

```bash
# Test CORS from different origin
curl -H "Origin: https://yourdomain.com" \
     -H "Access-Control-Request-Method: GET" \
     https://your-backend.onrender.com/health
# Should include Access-Control-Allow-Origin header

# Wrong origin
curl -H "Origin: https://malicious.com" \
     https://your-backend.onrender.com/health
# Should NOT include Access-Control-Allow-Origin header
```

### 16. Authentication Testing

```bash
# Test JWT expiration
# 1. Login and get token
TOKEN=$(curl -X POST https://your-backend.onrender.com/api/auth/login \
  -d '{"username":"...","password":"..."}' | jq -r '.access_token')

# 2. Verify token works
curl -H "Authorization: Bearer $TOKEN" \
     https://your-backend.onrender.com/api/documents

# 3. After expiration (1 hour), token should fail
# curl -H "Authorization: Bearer $TOKEN" \
#      https://your-backend.onrender.com/api/documents
# Should get 401 Unauthorized
```

## Security Incident Response

### If Secret is Leaked

1. **Immediately**:
   - [ ] Rotate the leaked secret in cloud service dashboard
   - [ ] Update `.env` locally with new secret
   - [ ] Redeploy services
   - [ ] Check audit logs for unauthorized access

2. **Within 24 hours**:
   - [ ] Review all API calls for suspicious activity
   - [ ] Check database for unauthorized changes
   - [ ] Monitor for related incidents

### If Database is Compromised

1. **Immediately**:
   - [ ] Take database offline (if possible)
   - [ ] Restore from backup
   - [ ] Reset all user passwords
   - [ ] Audit recent queries

2. **Within 24 hours**:
   - [ ] Review database access logs
   - [ ] Verify backups are clean
   - [ ] Test recovery procedure
